## Método y resultados

Todas las ejecuciones del artefacto usaron `env -i`, HOME/XDG vacíos bajo el laboratorio, `OPENCODE_DB` apuntando a una DB temporal, proyecto sintético y `TMPDIR` dentro del perfil. Se fijaron `OPENCODE_DISABLE_PROJECT_CONFIG=1` y `OPENCODE_CONFIG_PROJECT_DISABLE=1`. No se leyó ni ejecutó el perfil, la configuración, las credenciales, las sesiones ni el helper privado de v1. No se instalaron paquetes ni se modificó el runtime global.

La primera ejecución de `--version`/`--help` se hizo con un entorno vacío que no incluía `TMPDIR`, por lo que el runtime intentó crear `/tmp` y recibió `EROFS`. Al repetir con `TMPDIR` sintético —el requisito de este entorno— ambas pruebas pasaron. Esto fue una omisión del laboratorio, no un fallo del artefacto.

## Causa del fallo de los arranques upstream

Al ejecutarse mediante el loader glibc, `process.execPath` es la ruta del loader. En el source del tag, `packages/cli/src/util/process.ts` hace que `selfCommand()` devuelva solo `process.execPath` cuando el runtime no se identifica como Bun o Node. El modo `--standalone` agrega `serve --stdio --port 0`; el arranque normal usa `packages/cli/src/services/service-config.ts`, que agrega `serve --service`. Ambos relanzan el loader sin el binario `opencode` ni `--library-path`, y el loader interpreta `serve` como el archivo ELF.

El servidor y la TUI funcionan cuando el runner los separa explícitamente: inicia el ELF como `loader --library-path ... opencode serve --port 0`, y conecta el cliente con `--server`. La contraseña se genera para esa invocación y no se imprime; el runner cierra y espera su proceso servidor al terminar. Esta ruta conserva una invocación cotidiana sin depender de los relanzamientos upstream. No se ensayaron parches binarios, `patchelf`, runtimes alternativos, paquetes nuevos ni modificaciones del loader.

## Límites y decisión

- La etapa C confirma compatibilidad experimental con un runner temporal; no habilita el registro `opencode-v2` ni la instalación hasta integrar, auditar y probar ese runner según las etapas D/E.
- No se instalaron ni actualizaron v1 o v2. No se ejecutó `verify.sh` contra una instalación real.
- No se hicieron solicitudes a proveedores ni a Internet desde OpenCode. El único tráfico de la CLI fue contra `127.0.0.1`; la descarga del tarball fue la operación de red autorizada.
- Quedan sin ejecutar: herramientas de agente/subprocessos locales, DNS/TLS externo, policy prompt, pruebas negativas de configuración/plugins/ancestros, mediciones de rendimiento y comparación con v1.
- El servidor de laboratorio se cerró de forma normal; las DB, logs y fixtures permanecen en el temporal indicado para reproducción y no contienen datos privados.

No promover este candidato hasta integrar el runner en el wrapper, validar su manejo de argumentos/señales/lock y repetir las pruebas afectadas con el artefacto exacto.
