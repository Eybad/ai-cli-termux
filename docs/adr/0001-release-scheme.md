# Distribution releases in a dedicated repo

CI-compiled binaries ("CI build" pattern, currently only codex) are published as releases in a dedicated distribution repository (`Eybad/ai-cli-termux-dist`), not in the project repository: the project's releases page stays reserved for project releases (`v1.0.0+`), and the dist repo scales to N compiled tools without noise. The installer resolves the latest installable version by filtering releases by asset (expanded `ARCHIVE_TEMPLATE`) instead of `releases/latest`, because the dist repo hosts releases for multiple tools as well as assetless releases.

Upstream version mirroring (`vX.Y.Z` = `openai/codex` version) was chosen over a separate series (`v0.1.0`): `verify.sh` compares the executed version against the manifest, and `sha256.txt` pinning indexes by tag — mirroring makes both work seamlessly.

Cross-repo publishing: the workflow runs in the project repo and publishes to dist using a user fine-grained PAT (secret `DIST_REPO_TOKEN`); the workflow's `GITHUB_TOKEN` cannot write to another repo. SLSA attestation is issued by the project repo (where the workflow runs), which is why `registry/codex.conf` sets `ATTEST_REPO` pointing to the issuing repo.

## Patch series with semver build metadata (vX.Y.Z+androidN)

When the Android build needs a patch on top of upstream source (not the official binary + patchelf, but code compiled differently), the dist tag carries **semver build metadata** (`vX.Y.Z+androidN`, `N` = `patch_rev`, default 1):

- **The patch is generated, not checked in**: `scripts/gen-codex-lock-patch.py` rewrites upstream source deterministically and fail-closed. It has two modes: strict verification against `INVENTORY` (used locally and as a documented baseline) and `--dynamic` mode in CI (patches scanned call sites while guarding the build with a triple fail-closed gate: minimum site sanity threshold, static leak detection for unhandled receivers, and strict `rustc` type checking at compile time). The workflow applies the generator to the source checkout and compiles; an unpatched binary is never published. When upstream names a `File` with a receiver that does not reveal its type (v0.169.0 uses `opening` and `coordination` in `writer_lock_tests.rs`), the leak gate fails closed; this is resolved by allowlisting file→receiver pairs in `EXPLICIT_FILE_RECEIVERS`, which scans them across multi-line wrapped calls while keeping any other receiver or file fail-closed.
- **Why not `vX.Y.Z+1` or a separate series (`v0.146.0.1`)**: build metadata is ignored in semver precedence (no risk of accidental "upgrade" to the broken release) and Cargo accepts `version = "0.146.0+android1"` (`CARGO_PKG_VERSION` reports it, `cargo update --workspace` resyncs the lockfile). A separate series would break version mirroring (`verify.sh` compares the reported version against the manifest).
- **The installer supports it as the general case**: `install.sh` preserves `+build` in both version and tag (`parse_version_tag`; the tag is reconstructed from the full version including `+build`, not from the core) and `check_current` compares the **manifest tag** (identifying the exact release: `v0.146.0` ≠ `v0.146.0+android1`, so `--update` migrates from the broken release to the patched one). Both `verify.sh` and `install.sh` (`verify_install`) compare **normalized cores** (`normalize_version` extracts `X.Y.Z`), so the official `amd64` asset (which reports `0.146.0`) coexists under the same tag without spurious warnings.
- **Known limitation**: `--update` selects the "latest version" by API ordering (sorted by release creation date); it assumes `vX.Y.Z+androidN` is published after the broken release of the same core. This holds in the current flow (post-failure re-release), though if a patched tag were ever published before the standard one of the same core, `--update` would not pick it — accepted.
- **Intentional charset drift**: the workflow validates `+android[0-9]+` (strict `DIST_TAG` regex in `build-codex.yml`), whereas `install.sh` accepts any generic semver `+build`. This is deliberate: the workflow only emits `+androidN`, while the installer is generic by design. No cross-test exists — it would only fail silently if the scheme changed on one side.
- **Re-issuing a fix**: `patch_rev=2` → `vX.Y.Z+android2` (the idempotency gate checks the dist tag, not the upstream version). If upstream fixes the issue in std, `android_patch=false` reverts to the standard tag.
- **Fail-closed fallback**: if the patch does not apply (upstream source changed), the workflow aborts and the last good version remains installable.

Current use case: `File::{try_,}{lock,lock_shared}` return `Unsupported` on Android since Rust 1.89 (`flock` is not used on that target; `rust-lang/rust#148325`) → codex TUI/exec fail. The `file_lock_shim` shim calls `flock(2)` directly on Android (`EWOULDBLOCK` → `std::fs::TryLockError::WouldBlock`) and delegates to `std` outside Android.

### Detail: call sites carry the `crate::` prefix

The generator replaces each call site with `crate::file_lock_shim::<method>(&<recv>)`. The `crate::` prefix is **mandatory** (validated in CI): starting with Rust 1.96+, an unqualified path to a crate-root module no longer resolves when used from a nested submodule (`E0433`, even with `pub mod`); the `amd64` build (unpatched) compiles because upstream source does not use that pattern, and call sites in `lib.rs` itself (`arg0`, `message-history`) did not fail because they resolve from the root. The `patch_rev=2` fix (`v0.146.0+android2`) was precisely this: prefixing all 17 call sites (`amend.rs`, `certs.rs`, `writer_lock.rs`, etc.) with `crate::`.
